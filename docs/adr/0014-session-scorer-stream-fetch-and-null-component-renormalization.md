# F06.1 builds StravaStream + get_activity_stream() now; execution_score renormalizes weights around inapplicable components

Building F06.1 surfaced two decisions that break from prior tickets' established patterns.

**StravaStream gets built now, not deferred.** `time_in_zone_score` and `hr_drift_score` both require per-second HR stream data, which only exists behind Strava's separate `/streams` endpoint (§3.3) — `StravaActivity`'s aggregate fields (`average_heartrate`, `max_heartrate`) can't produce either component. F02.1 explicitly scoped `StravaStream`/`get_activity_stream()` out as "F06's time-in-zone analysis," and every ticket since (F04.1's health check, F05.1's Orchestrator classification) had deferred its integration-layer piece to a not-yet-built caller, keeping services pure. F06.1 breaks that pattern deliberately: it's the first ticket that structurally cannot produce two of its four required components without the stream, so `strava_adapter.py` gains `get_activity_stream(activity_id) -> StravaStream | None` (mirroring `MockWhoopAdapter`/`MockStravaAdapter`'s existing Real/Mock shape) rather than leaving a third named-but-undefined API type sitting in the docs. `session_scorer.py`'s own scoring functions remain pure — they take already-fetched stream data, not an adapter — the adapter method is what F02.1 was missing, not a violation of the pure-scoring-function principle.

**Null components renormalize the remaining weights to sum to 1.0.** §6.2 documents `time_in_zone_score = null` for Strength ("RPE only") but never states how the fixed weighted-sum formula (`time_in_zone*0.45 + hr_drift*0.25 + rpe*0.20 + load_delta*0.10`) handles a `None` component. We resolved this as renormalization: whichever components apply for a session type have their weights scaled up proportionally to sum to 1.0, so `execution_score` stays a genuine 0–100 scale regardless of session type — necessary since scores get compared across session types in monthly analysis (F08). The same reasoning extends to `hr_drift_score`, whose §6.2 mapping only covers "Zone 2 sessions" and "KEY sessions (HIIT, Threshold)" — Strength, Recovery, and Rest are uncovered because none has a meaningful aerobic-decoupling concept (Strength isn't HR-paced; Recovery/Rest are explicitly non-structured per §2.4). Applicability by session type: HIIT/Threshold/Zone2_Long/Zone2_Short use all 4 components; Strength uses only rpe (0.20) + load_delta (0.10), renormalized to 2/3 + 1/3; Recovery uses time_in_zone (Zone 1 target exists) + rpe + load_delta, renormalized to 60%/26.7%/13.3%. Rest has no structured activity to sync per §2.4 ("No structured activity. Passive recovery only") — the execution scorer never runs for Rest days at all, not a 5th null-handling case.

Alternative considered, for renormalization: keep each applicable component's literal weight and sum without rescaling, so Strength's max possible `execution_score` is structurally capped at 30 (`0.20 + 0.10`) even with perfect component scores. Rejected — it reads as a scoring bug to anyone comparing Strength sessions against Zone2 sessions in monthly analysis, when the actual intent is that all applicable signals contributed maximally.
