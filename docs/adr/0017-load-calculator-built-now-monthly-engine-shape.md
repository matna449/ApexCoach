# load_calculator.py built now; monthly_engine closes weekly_engine's deferred overreach signal; HRV trend re-derived, not stored incrementally

Building F08.1 surfaced that `services/load_calculator.py` — named in SDD's directory structure ("Grade-adjusted load, TSS-equivalent") — was never built by any prior ticket, despite the formula it should own being needed since F06.1: `session_scorer.score_load_delta(actual_load_au, planned_load_au)` has always taken `actual_load_au` as a parameter, meaning whoever eventually calls `session_scorer` was already expected to compute it externally. `activities.load_score` (the column meant to store it) has never been written by anything. Logic Spec §5.1's "Session Load Score (AU)" is the same formula SDD §5.2 already documents for HR-based sessions (`duration_minutes * avg_hr_bpm * grade_factor / 1000`), plus two more §5.1 adds: RPE-based for Strength (`duration_minutes * rpe / 6`) and duration-based for Recovery (`duration_minutes * 0.3`).

We're building `services/load_calculator.py` now, matching SDD's documented name and location, rather than inlining the formula as a private helper in `monthly_engine.py`. The formula is genuinely shared, not monthly-engine-specific — closing it here also retroactively unblocks whatever ticket eventually wires the real Strava-sync-and-score flow that `session_scorer` needs. Same pattern as building `StravaStream` when F06.1 first structurally needed it (ADR-0014): close a real, reusable gap at the point something first requires it, in the module the docs already named for it.

Two smaller decisions, following established precedent directly rather than opening new questions: `monthly_targets.hrv_trend_json` is recomputed fresh from `daily_metrics` each time `monthly_engine` runs (grouping HRV readings by week and averaging), not maintained as an incrementally-appended stored list — the same "re-derive from the single source of truth" reasoning as `recovery_band` in ADR-0016. And this ticket produces the actual signal `weekly_engine.run_weekly_adaptation()`'s `monthly_overreach_detected` parameter was left deferred for (ADR-0016): `monthly_engine.load_overreach_detected()` returns the boolean weekly_engine's caller now has a real source for, and this ticket's AC-mandated authority-hierarchy test (Three-Horizon Model, ADR-0002) feeds it into `run_weekly_adaptation()` and confirms the state machine forces `RECOVERY_WEEK` regardless of weekly-level signals — proving monthly's authority is enforced, not just documented.

`monthly_engine.py` itself follows F07.1's already-established functional-core-plus-thin-I/O-shell architecture (ADR-0016) — not re-litigated here, just reapplied: pure functions for load accumulation, forecast, and summary generation, one impure entry point that reads `metrics_repository`/`plan_repository` and writes `monthly_targets.month_summary_json` back.

Alternative considered: inline the load_au formula in `monthly_engine.py`. Rejected — SDD already names this as its own service, and leaving it inline would mean the eventual session_scorer caller either duplicates the formula or reaches into a module that doesn't conceptually own it.
