# weekly_engine: functional core + thin I/O shell, OVERREACHED added to the schema, recovery_band re-derived not persisted, monthly overreach deferred as a parameter

Building F07.1 surfaced one schema gap and confirmed a shape question every prior engine ticket had implicitly answered the same way.

**Functional core, imperative shell — same as every other engine.** Every prior engine (`daily_engine`, `session_scorer`, `orchestrator`, `health_check`) is a pure function with a thin `persist_*()` wrapper. SDD's own Module Contract row documents `weekly_engine`'s test strategy as "Integration," unlike every other engine's "Unit" — which looked like a signal this module should abandon the pure-core pattern and take repositories directly throughout. It doesn't need to: the decision logic itself (state transition rules, Skip Disposition criteria, reschedule-slot selection) stays pure, taking already-resolved values and returning a decision — this is what makes §4.2's exact criteria unit-testable the same way `daily_engine`'s decision trees are. One thin orchestrating function, `run_weekly_adaptation(plan_repo, metrics_repo, week_start_date, ...)`, does the actual reads (`weekly_plans`, `monthly_targets`, `daily_metrics` history) and the write-back — the same shape as `session_scorer.score_session()` + `persist_session_score()`, just consolidated into one entry point because this module's reads genuinely span three tables instead of zero. SDD's "Integration" label describes which test is most valuable for this module (verifying the read/decide/write wiring), not that its core logic must be impure.

**`OVERREACHED` was missing from the schema.** §4.1 documents 5 states (`ON_TRACK`, `LOAD_DEFICIT`, `OVERREACHED`, `RECOVERY_WEEK`, `COMPLETE`), but `weekly_plans.week_status`'s CHECK constraint (F10.1) only had 4 — `OVERREACHED` was never added. New Alembic migration adds it, same pattern as `monthly_targets.updated_at` (ADR-0012): a gap discovered while building the ticket that actually needs the missing piece, fixed via migration rather than worked around.

**`recovery_band` is re-derived, not persisted.** §4.2's Recovery Week trigger needs "2 consecutive days have `recovery_band == RECOVERY_RED`," but `recovery_band` is never stored anywhere — it's computed transiently by `orchestrator.classify_recovery()` from `daily_metrics.whoop_recovery_pct` and hand to `daily_engine`, then discarded. `run_weekly_adaptation()` re-derives it on demand by calling `classify_recovery()` against the last 2 days' stored `whoop_recovery_pct` values rather than adding a redundant column — it's a pure function over data already at rest, cheap to recompute, and avoids a second source of truth that could drift from the raw value.

**`monthly_engine.load_overreach_detected()` is a deferred parameter, not a real call.** Same problem `daily_engine` hit with `weekly_engine.check_recovery_week_trigger()` (ADR-0015): `monthly_engine` (F08) doesn't exist yet. `run_weekly_adaptation()` accepts `monthly_overreach_detected: bool | None = None`, defaulting to not-triggered until a caller can supply it. The *other* Recovery Week trigger condition (2 consecutive RED days) doesn't need this — it's computed directly from `daily_metrics` history weekly_engine already has access to.

**`weekly_plans`' JSON columns get a concrete shape**, since none is documented anywhere beyond "JSON array of planned sessions": `planned_sessions_json` / `adapted_plan_json` are `list[{"day": str, "session_type": str}]`; `skipped_sessions` is `list[{"session_type": str, "disposition": "rescheduled" | "written_off", "original_day": str}]`. Day-keyed session types are the minimum §4.2's slot-selection algorithm needs (find a non-KEY, non-Rest day with ≥1 day gap from any KEY session), and `skipped_sessions`' shape matches its own schema comment ("session types that were skipped and their disposition").

Alternative considered, for the architecture question: take repositories directly throughout every function, matching SDD's "Integration" label literally. Rejected — it would make the exact Skip Disposition/state-transition rules harder to unit test in isolation (every test would need a seeded DB even to check "does 84% monthly load correctly choose write-off"), for no real benefit over keeping those rules pure and only the orchestrator impure.
