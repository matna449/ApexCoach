# Adapters share an exception hierarchy, not a method Protocol; explain() returns a typed result, not a bare str

ADR-0002 established that WHOOP, Strava, and Ollama adapters each get a Real/Mock pair behind "one shared interface." Building F09.1 showed that claim can't mean a single `typing.Protocol` method signature — `ollama_adapter.explain(decision_context: dict) -> str` (API Contract §4.1), a future `whoop_adapter` returning a typed `WhoopDailyPayload`, and a future `strava_adapter` returning a typed `StravaActivity` share no common method shape. What genuinely repeats across all three is the *failure* shape: §6.1 (WHOOP), §6.2 (Strava), and §6.3 (Ollama) each describe the same pattern — attempt the real call, classify what went wrong, degrade gracefully, never crash or go silent.

We're defining a shared exception hierarchy in `adapters/errors.py` — `AdapterError` (base), `AdapterUnavailableError`, `AdapterTimeoutError`, `AdapterMalformedResponseError` — that every adapter's Real implementation raises internally to classify a failure before converting it into that adapter's own graceful-degradation output. Adapter-specific failure modes (e.g. Ollama's "model not pulled," which has no WHOOP/Strava analog) subclass the shared base (`OllamaModelNotFoundError(AdapterUnavailableError)`) rather than living in the shared module — the hierarchy is common, the leaves are adapter-specific. "Reused, not redefined by F01.1 and F02.1" means those tickets raise from this same hierarchy for their own transport failures, not that they implement an identical method signature.

Separately: API Contract §4.1 documents `explain() -> str`, but §6.3 requires the caller to know severity (WARN/INFO) and print a specific banner distinct from the explanation text — information a bare string can't carry as data. `explain()` returns `ExplanationResult` (`explanation: str | None`, `degraded: bool`, `banner: str | None`, `severity: Literal["WARN", "INFO"] | None`) instead. The adapter never prints or logs directly; it wraps every documented failure mode internally (raise the typed exception, catch it, convert to the appropriate `ExplanationResult`) and returns data. The caller — the Orchestrator or CLI, in a later ticket — decides what to print. This corrects API Contract §4.1's signature.

Alternative considered: keep `explain() -> str` literally and have the adapter call `click.echo()`/logging directly for the WARN/INFO banners as a side effect. Rejected because it mixes CLI-output concerns into the adapter layer, and would force `MockOllamaAdapter`'s failure-mode unit tests to capture stdout to assert correctness instead of inspecting a return value — exactly what this ticket's own acceptance criteria asks the tests to do ("unit test per failure mode asserting the correct graceful-degradation output... raw decision + WARN/INFO").
