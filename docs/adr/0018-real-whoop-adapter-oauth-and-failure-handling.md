# RealWhoopAdapter: hosted callback page + paste-back code, all 3 endpoints, retries live in the adapter, stale-data fallback deferred to the caller

Building F01.2 required turning API Contract §2.1's OAuth flow and §6.1's failure table into working code, not just documented behavior.

**A hosted callback landing page displays the code; the athlete pastes it back — corrected 2026-07-31, see below for the original (wrong) design.** WHOOP's redirect needs somewhere to land. `redirect_uri` points at a static page hosted on GitHub Pages (`https://matna449.github.io/ApexCoach/callback.html`, #34) that reads `code`/`state`/`error` from its own URL query string client-side and displays them; `run_authorization_flow()` prints the authorization URL, then prompts the athlete (`input_fn`, defaulting to `input()`) to paste the code and state back into the terminal, and validates the pasted state against the one generated at flow start before exchanging the code for tokens (#35). `adapters/oauth_pkce.py` keeps only the provider-agnostic PKCE/state generation (`generate_pkce_pair`, `generate_state`) — still reusable for Strava's OAuth flow (F02.2).

**Original design (superseded):** a temporary local HTTP server (`http://localhost:8080/callback`, `wait_for_callback()`) was meant to capture the redirect directly, the same pattern `gh auth login`/`gcloud auth login` use — with "manual URL paste" considered and rejected as a worse alternative (see below). Live-testing directly against WHOOP's developer portal app-registration form for #9 disproved this: WHOOP rejects `http://localhost` redirect URIs outright, accepting only an HTTPS URL on a domain you control or a custom URI scheme. The rejected alternative turned out to have the tradeoff backwards, once mixed-content and custom-URI-scheme registration were also ruled out (#34/#35).

**RealWhoopAdapter implements all 3 endpoints, not just `/v2/recovery`.** The ticket's "What to build" names only §2.2 (`GET /v1/recovery` in the original API Contract text), but its own acceptance criterion requires being "a drop-in replacement for MockWhoopAdapter behind the shared interface" — and `MockWhoopAdapter.get_daily_payload()` (ADR-0011) already combines recovery, cycle, and sleep into one `WhoopDailyPayload`. A recovery-only real adapter couldn't actually replace the mock; `RealWhoopAdapter` calls all 3 endpoints (§2.2-§2.4) to match the contract it must satisfy.

**Endpoint paths and OAuth scope corrected to WHOOP's real v2 API (2026-07-31).** The above was originally written against `/v1/recovery`, `/v1/cycle`, `/v1/activity/sleep` and `WHOOP_SCOPE = "read:recovery read:sleep read:strain read:body_measurement"` — both wrong. Live-tested against WHOOP's actual developer portal for #9: WHOOP's v1 API is fully retired, only v2 exists (`/v2/recovery`, `/v2/cycle`, `/v2/activity/sleep`); `read:strain` isn't a real scope name (`read:cycles` is), `read:body_measurement` is unused, and `offline` was missing entirely — without it WHOOP never issues a `refresh_token`, so token refresh would have silently broken the first time an access token expired. Corrected scope: `"read:recovery read:cycles read:sleep offline"`. See #32.

**Retry logic lives inside the adapter; falling back to stale data does not.** §6.1 documents both — "retry after 60 seconds (max 3 retries)" for 429, "retry once after 30 seconds" for 500/503 — and a fallback behavior ("use last stored `daily_metrics` row") when retries are exhausted. Retries are a robustness property of the HTTP call itself, implemented in `RealWhoopAdapter._get()`. The stale-data fallback needs `metrics_repository` access, which the adapter layer doesn't own (ADR-0002: raw→classified translation and remediation decisions belong to the Orchestrator, not adapters) — `RealWhoopAdapter` raises a typed `AdapterError` after retries exhaust (`WhoopRateLimitError`, `WhoopServerError`, `WhoopPendingScoreError`, `WhoopReauthorizationRequiredError`), and the caller (Orchestrator, not yet built) decides whether to fall back to stored data, matching ADR-0010's established pattern.

**Records are validated as they're fetched, not batched at the end.** The first implementation fetched all 3 endpoints before constructing any Pydantic model, meaning a malformed recovery response still cost 2 more WHOOP API calls before the problem was discovered — wasteful against §7.1's documented low-frequency call budget. Fixed to validate each record immediately after its fetch, so a bad recovery response short-circuits before the cycle/sleep calls happen at all.

A related bug caught while writing tests, not a design decision: `_access_token()` originally called `token_repository.needs_refresh()` before checking whether a token existed at all — `needs_refresh()` raises a bare `ValueError` (not an `AdapterError`) when nothing has ever been saved, so an athlete who'd never run `connect-whoop` would hit an unhandled exception instead of a clear error. Fixed to check for a stored token first.

Alternatives considered for the final callback mechanism, once the local server was ruled out: a custom URI scheme (`whoop://...`) — rejected, needs OS-level app-bundle registration, impractical for a cross-platform Python CLI; the OAuth Device Authorization Grant (RFC 8628) — rejected, WHOOP doesn't support it; auto-forwarding the code from the HTTPS landing page to a local HTTP server via JavaScript — rejected, HTTPS pages calling `http://localhost` risk mixed-content blocking, unreliable across browsers. Manual copy-paste from a hosted page, once the only remaining option, turned out to be the robust choice rather than a fallback compromise.
