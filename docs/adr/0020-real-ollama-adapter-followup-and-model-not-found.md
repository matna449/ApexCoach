# RealOllamaAdapter: ask_followup() added to the shared interface, 404 assumed for model-not-found pending live verification, one live_llm test opt-in via pytest flag

Building F09.2 (#14) turned API Contract §4.2's `POST /api/chat` call into working code and closed a gap the ticket's own acceptance criteria exposed: "conversational follow-up ('why', 'what if I do it anyway')" is required by the PRD (§ features) and ADR-0001, but `OllamaAdapterProtocol` (F09.1, #3) only ever defined `explain(decision_context) -> ExplanationResult` — no follow-up method existed on the Protocol or `MockOllamaAdapter`.

**`ask_followup(decision_context, prior_explanation, question) -> ExplanationResult` added to the Protocol, `MockOllamaAdapter`, and `RealOllamaAdapter` together**, not just `RealOllamaAdapter` alone — this ticket's own AC requires `RealOllamaAdapter` to be "a drop-in replacement for MockOllamaAdapter behind the shared interface," which isn't possible if the Real adapter has a method the Mock and Protocol don't. Ollama's `/api/chat` endpoint natively supports multi-turn conversation via its `messages` array (system + user + prior assistant + new user), confirmed against Ollama's own API docs — `ask_followup()` rebuilds `explain()`'s system+user messages, appends the prior assistant reply and the new question, and reuses the same `_degrade_on_failure()` failure-classification path `explain()` uses. A single-shot follow-up (re-supplying the prior explanation as context) was chosen over full conversation-history threading — the CLI is a one-shot-per-morning-run tool, not a persistent chat session, so there's no state to thread a longer history through yet; if that changes, `ask_followup` is the natural place to extend.

**The explain()/ask_followup() failure-classification logic is shared via a module-level `_degrade_on_failure()` helper**, not duplicated per method or per adapter. Both `MockOllamaAdapter` and `RealOllamaAdapter` route their model call through it, so the two stay behaviourally identical by construction rather than by convention — a new failure mode only needs handling in one place.

**Model-not-found is assumed to surface as an HTTP 404 from `POST /api/chat`** — Ollama's public API docs (github.com/ollama/ollama/docs/api.md) don't document the exact error shape for an unpulled model, and it can't be verified without a live Ollama instance. This is a live-verification checkpoint, not a confirmed fact: docs/adr/0018 and 0019 both found real API behavior diverging from documented/assumed behavior (WHOOP's `/developer/` prefix, Strava's endpoint paths) — get the same live-or-nothing scrutiny in mind here. If live testing shows Ollama returns a different status or an error embedded in a 200 response body instead, `RealOllamaAdapter._chat()`'s 404 check is the one place to fix it.

**The live-call test is gated by a `--run-live-llm` pytest flag (`apex_coach/tests/conftest.py`), not `pyproject.toml`'s `addopts`.** SDD §7.2 requires the test to be "skipped in CI... run manually only as a smoke test." An `addopts = "-m 'not live_llm'"` default would need to be overridden on every manual run (`pytest -m live_llm` conflicts with the addopts default rather than replacing it — a known pytest marker-expression gotcha), so a custom `pytest_addoption`/`pytest_collection_modifyitems` hook skips `live_llm`-marked tests unless `--run-live-llm` is passed explicitly. `test_real_ollama_adapter.py`'s other tests (happy path, all 4 failure modes, request/message shape) run via `httpx_mock` against no real Ollama instance — fast, deterministic, CI-safe, and exercise `RealOllamaAdapter`'s own HTTP-level logic specifically, distinct from (but structurally mirroring) `MockOllamaAdapter`'s already-established simulated failure-mode tests from F09.1.
