# health_check.py's output includes the override boolean, stays pure/non-interactive this ticket, and daily_metrics gains a targeted update path

Building F04.1 surfaced one correction and one gap in ADR-0006's "daily_metrics is append-only" claim, plus two scoping questions Logic Spec §7 left open.

**daily_metrics needs two independent writers.** `daily_metrics.date` is UNIQUE and `metrics_repository` (F10.3) only exposed `insert_daily_metrics()`, per ADR-0006's blanket "daily_metrics, hr_zones, and session_scores are plain append-only inserts." That decision didn't anticipate that WHOOP fetch (F01.x) and the morning health check (this ticket) are two independent processes that both need to populate different columns of the *same day's row* — whichever runs second would hit a duplicate-key error re-inserting. We're adding `update_daily_metrics(date, **fields)` to `metrics_repository`; `health_check.py`'s persistence path checks `get_daily_metrics(date)` first and inserts if no row exists yet, updates if one does. Same shape as ADR-0006/0007's precedent: a table stays mostly append-only with one narrow, documented mutation path for a real multi-writer need, not a blanket exception.

**§7.3's override rule doesn't account for inverted-direction questions.** §7.3 says "IF any adaptive_health_check_score >= 4: FORCE ABORT," written as a blanket numeric rule. But §7.2's Recovery/Rest row defines its adaptive question (general wellbeing) as *inverted* — "<= 2: flag low wellbeing," where a high score is good, not concerning. Applying §7.3's rule literally would treat a wellbeing score of 5 (excellent) as a safety override trigger, which is backwards. `health_check.py` computes the override boolean only over "high is bad" (pain/discomfort-style) questions; the inverted wellbeing question is evaluated solely against its own §7.2 threshold, never against the §7.3 override.

**Scoping decisions, not corrections:** `health_check.py`'s output dict includes a computed `override_triggered: bool` (the §7.3 trigger, direction-aware as above) alongside the raw answers and §7.2's per-question flags — a pure computation over data already in hand, no DB access, no cross-day logic. It does not attempt §7.3's 3-consecutive-day `persistent_flag` tracking (needs cross-day queries and `decisions`-table writes — daily_engine/monthly_engine territory) or enforce FORCE ABORT itself (that's the actual Decision Output, owned by daily_engine per ADR-0001). Separately, this ticket does not wire an interactive CLI prompt — unlike F01.1/F02.1/F03.1, its own "What to build" never asks for one, and a standalone prompt divorced from the WHOOP fetch it's meant to run alongside would mean either throwaway CLI code or awkward retrofitting once the Orchestrator (F05.1) exists to sequence the real morning flow.

Alternative considered, for the dual-writer problem: health_check.py never touches `metrics_repository` directly, returning only a dict for the Orchestrator to merge with WHOOP data into one atomic insert. Rejected because it can't satisfy this ticket's own acceptance criterion ("Responses persisted via metrics_repository, retrievable by date") until F05.1 exists, and defers a real, already-visible problem rather than solving it now while the cost is one small repository method.
