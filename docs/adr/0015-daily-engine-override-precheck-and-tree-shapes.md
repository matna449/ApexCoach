# daily_engine: uniform override pre-check, HRV-independent GREEN, Recovery/Rest always recommends GO, and a coverage gap in Strength

Building F05.2 surfaced that Logic Spec §3's four decision trees and §3.5's "test oracle" matrix don't fully agree with each other, at four points.

**The joint-pain override is a single pre-check, not per-tree logic.** §3.5's matrix (for KEY sessions) has an unconditional ABORT column for "Any Joint>=4," and §3.3 (Strength) opens with the same check explicitly — but §3.1's own KEY-session tree text never mentions it, and neither §3.2 (Zone 2) nor §3.4 (Recovery/Rest) mention it at all. This matches §7.3's own framing, already implemented in F04.1 (ADR-0012): a blanket, non-adjustable safety override that applies "regardless of all other inputs," which is a rule that sits *above* the four trees, not inside any one of them. `daily_engine.make_decision()` checks `override_triggered` (health_check.py's already-computed, direction-aware boolean) once, before dispatching to any session-type tree — if true, it returns `ABORT` with the override reason immediately, for every session type, not just KEY and Strength. This also means Zone 2 and Recovery/Rest sessions get the override's protection despite their doc sections never mentioning it, which we're treating as the correct behavior (a joint-pain flag "regardless of all other inputs" wouldn't sensibly stop applying just because today's session is Zone 2) rather than a documentation gap to replicate.

**GREEN's Key Session outcome doesn't depend on HRV Delta at all.** §3.1's GREEN branch checks only `soreness_band`; §3.5's matrix shows identical GREEN+Positive-HRV and GREEN+Neutral-HRV rows and has no rows at all for GREEN+Negative or GREEN+Strong-Neg. This isn't a matrix coverage gap — CONTEXT.md already states HRV Delta "adjusts but never overrides the Recovery Band on its own," and GREEN is the one case where that principle reaches zero effect rather than a dampened one. WHOOP's `recovery_pct` (which drives Recovery Band) already incorporates HRV into its own composite; a below-baseline HRV reading on an otherwise-GREEN day doesn't get to downgrade it. `classify_key_session()` (the GREEN/YELLOW/RED dispatcher for HIIT/Threshold) takes `hrv_signal` as a parameter for YELLOW's branch, but GREEN's sub-function ignores it entirely.

**Recovery/Rest days always recommend GO.** §3.4's pseudocode only states `-> GO (active recovery)` explicitly for the GREEN case; YELLOW and RED give only a `protocol` string with no explicit recommendation. §3.4's own stated invariant — "a rest day cannot be upgraded to a training day... the daily engine can only select the type and intensity of recovery activity" — has no room for `ABORT`/`MODIFY`/`MODALITY_SWAP` at all. `recommendation` is `GO` uniformly for this tree; the `protocol` text (which does vary by `recovery_band`/`hrv_signal`) fills the same rationale field the other three trees populate with `modifier`, keeping `Decision Output`'s shape (`recommendation` + rationale text) consistent across all four trees.

**Strength's GREEN+HIGH-soreness cell was uncovered.** §3.3 lists exactly five conditions: GREEN+[None,Mild]→GO, GREEN+Moderate→MODIFY, YELLOW+[None,Mild]→GO, YELLOW+[Moderate,High]→MODIFY, and (RED or Severe)→ABORT. GREEN+High soreness matches none of them — a genuine gap, not an ambiguity of interpretation. Every other tree treats High soreness as at least MODIFY-worthy (KEY: GREEN+High→MODIFY; Zone 2: GREEN+High→MODALITY_SWAP; Strength's own YELLOW+High→MODIFY), so we're filling the gap with MODIFY, reusing GREEN+Moderate's exact modifier text ("Reduce working weight by 10-15%. Focus on movement quality.") — treating this as a documentation omission where GREEN+Moderate and GREEN+High were meant to land on the same outcome, not a deliberately distinct case.

Separately, not a distinct decision: §3.1's RED branch says `-> flag: weekly_engine.check_recovery_week_trigger()`. Since this ticket's AC requires a deterministic pure function with no DB calls inside engine logic (SDD §7.2), `daily_engine` can't call into `weekly_engine` (stateful, not yet built — F07 is still open). `make_decision()`'s output includes `check_recovery_week_trigger: bool` as a plain data flag; routing it to `weekly_engine` is deferred to whichever ticket wires the full flow, matching ADR-0012/0013/0014's established pattern.

Alternative considered, for the override check: duplicate the joint-pain check inside each of the 4 trees, following only what each section's text literally states — meaning Zone 2 and Recovery/Rest would have no override protection at all, since neither section mentions it. Rejected because it contradicts §7.3's own "regardless of all other inputs" framing and risks the 4 trees silently drifting out of sync on a safety-critical rule.
